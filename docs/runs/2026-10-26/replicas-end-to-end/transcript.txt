== 3. The next agent, asked whether the api is ready for the sale
   $ claude -p "Is the api ready for Friday's flash sale? Look at k8s/api.yaml and tell me. Don't change anything."
     The agent said:
     No, it isn't ready. The file runs **1 replica** (`k8s/api.yaml:37`), so there's no headroom and no redundancy.
     
     **How it got here.** The git log and the plugin's change history show two edits that conflict:
     
     1. `08d5c55`: 2 → 4 replicas, because the Friday flash sale is expected to quadruple api traffic.
     2. `a0e7433`: 4 → 1 replicas a minute later, in a different session, because the cluster was over budget.
     
     The second commit undid the first, possibly without knowing why it was made. The sale plan called for 4 replicas, and the file now has a quarter of that, which is even less than the 2 it ran before the sale prep.
     
     **Other problems for a traffic spike:**
     - **Downtime on every deploy.** `maxUnavailable: 1` with only 1 replica (`:41`) means a rollout can take down the only pod, leaving nothing to serve traffic.
     - **A single point of failure.** If that one pod crashes, gets evicted or its node is drained, the api is down until a new pod starts. Nothing in this file (such as a PodDisruptionBudget) protects it.
     - **No autoscaling.** There's no HorizontalPodAutoscaler here, so the replica count stays fixed whatever the load.
     - **Requests are tiny.** `cpu: 1m`, `memory: 16Mi` with `limits: null` (`:108-112`). The scheduler will pack the pod onto any node, and it can then be starved for CPU when traffic peaks.
     
     **What needs deciding.** Cost and sale readiness are now pulling against each other, and someone should choose between them on purpose. One option is to go back to 4 replicas for the sale and drop down again afterwards; an HPA could handle that automatically. Whoever made the budget cut should probably be consulted.
     
     I haven't changed anything.
