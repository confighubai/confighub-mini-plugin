# `cub mini` and plain `cub`

What you do with confighub mini on your laptop works the same on your organization's ConfigHub, because it is the same ConfigHub server and the same `cub`, ConfigHub's command-line tool. Each `cub mini` command runs `cub`'s own commands and fills in the rest of the request for you. So, except where the table says "Nothing yet", you can do everything shown with `cub mini` in plain `cub`, on any ConfigHub. The table lists which `cub` commands each `cub mini` command stands for.

| `cub mini` | Plain `cub` | What `cub mini` fills in |
|---|---|---|
| `cub mini install` | `cub server install` | The server and its PostgreSQL run as processes on this machine, with no Docker and no Kubernetes |
| `cub mini upload FOLDER --variant V` | `cub component create`, `cub space create`, `cub unit create`, `cub variant create` (or `cub variant upload`); where a copy waits for approval, `cub function set --change-desc` on the base and `cub changeorder create` | The Component is named after the folder. The base and the copy are made. The copy is aimed at the hub's cluster, when there is one. Where a copy takes changes only once approved, the files' changed values are set in the base with the reason and asked for with a change order of this upload's own, so two agents uploading at once, in the same second included, each get an order that describes their own change. Changed means changed in this folder: `.confighub-app`, which `adopt` writes and you commit, notes what the files last matched in the hub, and only a value that differs from it is proposed, so a clone proposes only what it changed. A file that is one environment's own, `.env.staging` or `staging.tfvars`, is set as that copy's own values instead |
| `cub mini adopt DIR [--name NAME] [--pattern APP] [--dry-run]` | `cub component create`, `cub space create`, `cub unit create`, `cub variant create`, `cub function set --protect` for each copy's own values, and `cub changeworkflow create` for the live copy | An app from what the folder reads at start: `.env` or `app.env`, a compose file's environment, `.env.example`, and the settings the code reads, with their defaults; or a Terraform folder's `common.tfvars`. Three Spaces: `APP-base`; `APP-staging`, with the values now; and `APP-live`, which takes them only once you approve. A `.env.staging` or `staging.tfvars` is staging's own values from the start, `.env.production` or `prod.tfvars` live's. A secret's value is left out and named. Your files are not changed, and `.confighub-app` is written beside them. With `--pattern APP`, the app is made from an app already in the hub, keeps its own values, and takes what that app changes next with `cub mini upgrade APP-base/app` |
| `cub mini adopt DIR` on a Kustomize repository | The same | `base/`, as kustomize renders it, becomes `APP-base`. What `overlays/staging` changes becomes staging's own values, field by field, and what the prod, production or live overlay changes, or the one an Argo CD Application deploys, becomes live's |
| `cub mini set COMPONENT FUNCTION ARG --variant V` | `cub function set --space COMPONENT-V --unit UNIT FUNCTION ARG` | The Space and Unit are found. The value is marked as kept, so a later version does not replace it. The reason is recorded beside it |
| `cub mini promote COMPONENT-V` | `cub variant promote COMPONENT-V`, then `cub release publish COMPONENT-V` | The preview shows each value taken and each value kept. The result is released to the cluster |
| `cub mini require-approval COMPONENT --variant V --agent NAME` | `cub changeworkflow create`, `cub component update`, `cub serviceaccount create` and `key add`, and permissions on each Space | The whole approval gate in one step, plus the agent's own `cub` configuration and its Claude Code settings. [Approvals](approvals.md) shows the same steps with plain `cub` |
| `cub mini pull-key NAME COMPONENT --variant V [--secrets]` | `cub serviceaccount create`, `cub serviceaccount key add`, and `View` on the variant's Space | A key for the machine that runs the service, with the right to read that one copy and nothing else; with `--secrets`, also that copy's secrets, `COMPONENT-V-secrets` |
| `cub mini secret set APP KEY[=VALUE] --variant V --change-desc WHY`, `cub mini secret list APP --variant V`, `cub mini secret files APP --variant V --dir DIR` | A Space of its own, `APP-V-secrets`, holding one Unit, `secrets`, made with `cub space create` and `cub unit create`; `files` reads it as `cub unit data` does | A secret the app reads when it runs, kept under your key, which no agent's key is given a right to: the agent that `require-approval --agent` made can change the base and propose, and cannot read it. With no `=VALUE`, the value is read from standard input, so that it is on no command line. The app's settings name it, `KEY_FILE=/run/secrets/APP/KEY`, never its value. `files` writes each secret as `DIR/KEY`, readable by that user only, on the machine that runs the app, with a key from `pull-key --secrets`. `list` names the secrets and who may read them, and never prints a value |
| `cub mini pull COMPONENT --variant V --dir DIR` | `cub unit data`, for each Unit of the variant | On the machine that runs the service: the copy written as its files, the hub's marker left out, the service restarted with `--restart` only when a file changed; `--timer 30s` makes it a systemd timer |
| `cub mini waiting` | `cub changeorder list`, `cub space list` | Each change order still on its way, what it is for, and the command that approves it |
| `cub mini approve [BASE/ORDER or SPACE]` | `cub variant approve BASE --change-order BASE/ORDER --note WHY` with what you read kept as claims, then `cub mini promote SPACE --change-order BASE/ORDER` | Shows the change first and asks; one command where `cub` needs two |
| `cub mini refuse [BASE/ORDER or SPACE] --reason WHY` | `cub changeorder update ORDER --space BASE --aborted-reason WHY` | Names the change the way `cub mini waiting` does |
| `cub mini copy --to-dir`, `--from-git`, `--to-file`, `--from-file` | Nothing yet | Writes the work out as plain files, with a `CHANGES.md` that says why each value is set. Reads it back in from Git, with each commit's reason. Moves it between hubs |
| `cub mini connect`, `offer`, `offers` | Nothing yet | Makes the organization's ConfigHub the parent of a confighub mini's work, and offers changes up to it |

Where the table says "Nothing yet", plain `cub` has no equivalent, and only `cub mini` does it for now. These are the commands that carry work between hubs: out to files and Git, and up from a hub of your own to your organization's ConfigHub.

## Words used in the table

- A *hub* is one running ConfigHub server. *confighub mini* runs a hub on one machine.
- A *Space* holds configuration, as *Units*: one Unit per file or resource.
- A *Component* is one piece of software. Its *base* is the version you change. A *variant*, such as `live`, is a copy made from the base for one place it runs. Its Space is named `COMPONENT-V`, such as `api-live`.
- To *promote* a variant is to bring the base's changes into it. A *release* is a published version of a variant that a cluster pulls.
- A *ChangeWorkflow* says what a change needs before it reaches a variant, such as a person's approval. A *service account* is the identity an agent uses, with a key of its own.
