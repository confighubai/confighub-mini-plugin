# `cub mini` and plain `cub`

What you do with confighub mini on your laptop works the same on your organization's ConfigHub, because it is the same ConfigHub server and the same `cub`, ConfigHub's command-line tool. Each `cub mini` command runs `cub`'s own commands and fills in the rest of the request for you. So, except where the table says "Nothing yet", you can do everything shown with `cub mini` in plain `cub`, on any ConfigHub. The table lists which `cub` commands each `cub mini` command stands for.

| `cub mini` | Plain `cub` | What `cub mini` fills in |
|---|---|---|
| `cub mini install` | `cub server install` | The server and its PostgreSQL run as processes on this machine, with no Docker and no Kubernetes |
| `cub mini upload FOLDER --variant V` | `cub component create`, `cub space create`, `cub unit create`, `cub variant create` (or `cub variant upload`); where a copy waits for approval, `cub function set --change-desc` on the base and `cub changeorder create` | The Component is named after the folder. The base and the copy are made. The copy is aimed at the hub's cluster, when there is one. Where a copy takes changes only once approved, the files' changed values are set in the base with the reason and asked for with a change order of this upload's own, so two agents uploading at once, in the same second included, each get an order that describes their own change. Changed means changed in this folder: `.confighub-app`, which `adopt` writes and you commit, notes what the files last matched in the hub, and only a value that differs from it is proposed, so a clone proposes only what it changed. A copy that takes changes now, such as staging, has them at once, except a value it keeps as its own, and the upload says which. A file that is one environment's own, `.env.staging` or `staging.tfvars`, is set as that copy's own values instead. For an app adopted from a Kustomize repository, the repository is rendered as adopt renders it: what the base renders differently is proposed field by field, what each overlay now sets differently is that copy's own, and a resource an overlay adds stays in the repository, named. With `--dry-run`, it says what it would set and propose, and changes nothing |
| `cub mini adopt DIR [--name NAME] [--pattern APP] [--dry-run]` | `cub component create`, `cub space create`, `cub unit create`, `cub variant create`, `cub function set --protect` for each copy's own values, and `cub changeworkflow create` for the live copy | An app from what the folder reads at start: `.env` or `app.env`, a compose file's environment, `.env.example`, and the settings the code reads, with their defaults; or a Terraform folder's `common.tfvars`. Three Spaces: `APP-base`; `APP-staging`, with the values now; and `APP-live`, which takes them only once you approve. A `.env.staging` or `staging.tfvars` is staging's own values from the start, `.env.production` or `prod.tfvars` live's. A secret's value is left out and named. Your files are not changed, and `.confighub-app` is written beside them. With `--pattern APP`, the app is made from an app already in the hub, keeps its own values, and takes what that app changes next with `cub mini upgrade APP-base/app` |
| `cub mini adopt DIR` on a Kustomize repository | The same | `base/`, as kustomize renders it, becomes `APP-base`. What `overlays/staging` changes becomes staging's own values, field by field, and what the prod, production or live overlay changes, or the one an Argo CD Application deploys, becomes live's |
| `cub mini try APP NAME [--from staging\|live]`, `--keep --change-desc WHY`, `--drop` | A Space of its own, `APP-try-NAME`, made with `cub space create` and `cub unit create` from staging's Unit, or live's; `--keep` is `cub function set --change-desc` on the base and staging and `cub changeorder create` for live; `--drop` is `cub space delete` | A copy of the app for one try, in about a tenth of a second, that nothing in staging or live takes from. It prints how to change it, `cub mini set APP KEY=VALUE --variant try-NAME`. `--keep` gives what the copy holds differently to the base with the reason and to staging at once, puts it behind a change order for live, and removes the copy. `--drop` removes the copy and says what it held |
| `cub mini tries APP` | `cub space list`, `cub unit data` | Each try of the app: how old it is, what it was made from, and what it holds differently |
| `cub mini provide NAME KIND KEY=VALUE --for staging\|live --change-desc WHY` | `cub space create services` and `cub unit create --space services NAME`; for a copy behind approval, `cub changeorder create` | A service that provides `postgres`, `redis`, `s3` or `mail`, registered as `services/NAME` for one copy, or for any. A value that holds a password or a token is refused, naming `cub mini secret set`. Every copy that needs KIND and has no provider takes it. Registered again, its new values reach every copy that takes changes at once, such as staging; a copy behind approval, such as live, keeps what was approved, and the new values are proposed to it with a change order that waits for you. An agent's key may not register a provider |
| `cub mini need APP KIND [--variant V] [--provider NAME]` | `cub function set` on the base for each setting, and `cub link create` from each copy to its provider; for a copy behind approval, `cub changeorder create` | The base names the settings KIND is read by (`DATABASE_URL`, `REDIS_URL`, ...) with no value yet. A copy that takes changes at once, such as staging, takes its own provider's values as its own, and follows the provider when it changes. A copy behind approval, such as live, is written nothing: its provider's values are proposed with a change order of their own, which `cub mini waiting` lists and `cub mini approve` puts in. A later version of the base does not overwrite them. A copy with no provider says what it needs. An agent's key can run it, and so propose |
| `cub mini needs [APP]` | `cub link list`, `cub unit data` | What each copy needs, from which provider, what waits for approval, and what is still unmet |
| `cub mini set COMPONENT FUNCTION ARG --variant V` | `cub function set --space COMPONENT-V --unit UNIT FUNCTION ARG` | The Space and Unit are found. The value is marked as kept, so a later version does not replace it. The reason is recorded beside it |
| `cub mini promote COMPONENT-V` | `cub variant promote COMPONENT-V`, then `cub release publish COMPONENT-V` | The preview shows each value taken and each value kept. The result is released to the cluster |
| `cub mini require-approval COMPONENT --variant V --agent NAME` | `cub changeworkflow create`, `cub component update`, `cub serviceaccount create` and `key add`, and permissions on each Space | The whole approval gate in one step, plus the agent's own `cub` configuration and its Claude Code settings. The agent may change the base and each copy that takes changes at once, such as staging, and propose; it cannot write, approve or promote into a copy behind approval, or read a secret, whatever order the copies were put behind approval in. The command says which copies each agent may change, and when one it could change at once is now behind approval, it says the agent no longer can. [Approvals](approvals.md) shows the same steps with plain `cub` |
| `cub mini reach NAME` | `cub space list` and the permissions on each Space, Unit and Component, asked of the hub with the agent's key | What one agent's key reaches, right by right: which Spaces and Units it can change, and how many it can only read. What is at risk if the key is taken |
| `cub mini pull-key NAME COMPONENT --variant V [--secrets]` | `cub serviceaccount create`, `cub serviceaccount key add`, and `View` on the variant's Space | A key for the machine that runs the service, with the right to read that one copy and nothing else; with `--secrets`, also that copy's secrets, `COMPONENT-V-secrets` |
| `cub mini secret set APP KEY[=VALUE] --variant V --change-desc WHY`, `cub mini secret list APP --variant V`, `cub mini secret files APP --variant V --dir DIR` | A Space of its own, `APP-V-secrets`, holding one Unit, `secrets`, made with `cub space create` and `cub unit create`; `files` reads it as `cub unit data` does | A secret the app reads when it runs, kept under your key, which no agent's key is given a right to: the agent that `require-approval --agent` made can change the base and propose, and cannot read it. With no `=VALUE`, the value is read from standard input, so that it is on no command line. The app's settings name it, `KEY_FILE=/run/secrets/APP/KEY`, never its value. `files` writes each secret as `DIR/KEY`, readable by that user only, on the machine that runs the app, with a key from `pull-key --secrets`. `list` names the secrets and who may read them, and never prints a value |
| `cub mini pull COMPONENT --variant V --dir DIR` | `cub unit list`, then `cub revision data` for each listed revision | On the machine that runs the service: the copy written as its files, the hub's marker left out, the service restarted with `--restart` only when a file changed; `--timer 30s` makes it a systemd timer |
| `cub mini waiting` | `cub changeorder list`, `cub space list` | Each change order still on its way, what it is for, and the command that approves it |
| `cub mini approve [BASE/ORDER or SPACE]` | `cub variant approve BASE --change-order BASE/ORDER --note WHY` with what you read kept as claims, then `cub mini promote SPACE --change-order BASE/ORDER` | Shows the change first and asks; one command where `cub` needs two |
| `cub mini refuse [BASE/ORDER or SPACE] --reason WHY` | `cub changeorder update ORDER --space BASE --aborted-reason WHY` | Names the change the way `cub mini waiting` does |
| `cub mini copy --to-dir`, `--from-git`, `--to-file`, `--from-file [--name NAME]` | Nothing yet | Writes the work out as plain files, with a `CHANGES.md` that says why each value is set. Reads it back in from Git, with each commit's reason. Moves it between hubs, as a file that carries every kept value's reason whole; a copy that fails leaves nothing behind. `--from-file FILE --name NAME` takes in a setup someone shared under a name of its own, `NAME-base`, `NAME-staging`, ..., and prints the next step, `cub mini adopt FOLDER --pattern NAME`, which makes your own app from it |
| `cub mini connect`, `offer`, `offers` | Nothing yet | Makes the organization's ConfigHub the parent of a confighub mini's work, and offers changes up to it |

Where the table says "Nothing yet", plain `cub` has no equivalent, and only `cub mini` does it for now. These are the commands that carry work between hubs: out to files and Git, and up from a hub of your own to your organization's ConfigHub.

## Words used in the table

- A *hub* is one running ConfigHub server. *confighub mini* runs a hub on one machine.
- A *Space* holds configuration, as *Units*: one Unit per file or resource.
- A *Component* is one piece of software. Its *base* is the version you change. A *variant*, such as `live`, is a copy made from the base for one place it runs. Its Space is named `COMPONENT-V`, such as `api-live`.
- To *promote* a variant is to bring the base's changes into it. A *release* is a published version of a variant that a cluster pulls.
- A *Link* ties one Unit to another, so that a value in one comes from the other. The hub keeps it resolved, so a change to the provider reaches the copy.
- A *ChangeWorkflow* says what a change needs before it reaches a variant, such as a person's approval. A *service account* is the identity an agent uses, with a key of its own.
